The shape of the load

This is a caching problem, not a database problem.

Assume 5M profiles averaging 150 views a month: roughly 750M page views against about 30M edits. A read-to-write ratio near 25,000 to 1, where every read is a public page that can be rendered before anyone asks for it.

The consequence: capacity planning is about hit rate and bandwidth, not query throughput. A single Postgres primary absorbs the write side three orders of magnitude over.

Architecture

Six decisions that carry the whole system.

Edge first
Each profile renders to static HTML and lives on the CDN, revalidated in the background, with a publish purging exactly one path. At 97% hit rate the origin sees under 100 requests a second.
Origin
Stateless app servers, Postgres primary with read replicas, Redis for hot metadata, sessions, rate limits and cached assistant answers.
Data shape
Profiles and blocks are relational rows with block props in JSONB — 41 block types with different fields do not belong in rigid columns, and JSONB keeps schema changes out of migrations.
Media
Object storage behind an image CDN that resizes and re-encodes on request. Never serve an original; never store four sizes of the same photo.
Analytics
Never one database row per page view. Count at the edge, aggregate per minute, land it in a columnar store. This is the first thing that breaks if it is got wrong.
Assistants
Embeddings per knowledge passage in pgvector while volumes are small; a dedicated vector store past roughly 50M vectors. Cache answers by profile and normalised question — the same handful of questions arrive over and over.
Recommended stack · Core

What the product is actually built on.

FrameworkNext.js · App Router

Why: per-profile static generation with on-demand revalidation is the single feature this architecture leans on hardest. Server components keep the public page light while the editor stays fully client-side. The demo already runs on it.

LanguageTypeScript, strict

The block registry, props and content model are all typed end to end. This is what makes 41 block types maintainable by a small team.

HostingVercel → Cloudflare in front

Vercel for the tightest Next integration and preview deploys. Cloudflare in front for custom domains, WAF and caching control — and as the exit path if egress pricing bites at Phase 2.

DatabasePostgreSQL — Neon, then Aurora

Relational profiles, JSONB blocks, row-level security for tenancy and pgvector for embeddings, all in one engine. Neon's branching gives every pull request a real database.

Data accessDrizzle ORM

SQL-first with real TypeScript inference and a tiny runtime that works at the edge. Prisma is the safe alternative; its heavier client is the reason it is second here.

AuthClerk

Organisations map cleanly onto "a profile is a tenant", and it ships MFA and user management rather than us building them. Auth.js is the no-vendor fallback if that matters more than speed.

Storage & mediaCloudflare R2 + Images

Zero egress fees. At 50TB of galleries served hundreds of millions of times, egress is the decisive line on the bill — this one choice is worth more than every other cost optimisation combined.

StylingTailwind + CSS variables

Already proven in the demo: a template swap repaints the public page, the editor and the admin by changing variables, with no per-component theming.

Recommended stack · Services

Everything the page does not render itself.

Cache & limitsUpstash Redis

Serverless, HTTP-addressable so it works from the edge. Holds hot profile metadata, rate limits and the assistant answer cache.

Background jobsInngest

Durable, TypeScript-native, with retries and observability built in. Email, SMS, embedding jobs and analytics roll-ups all belong here — nothing a visitor waits on should call a third party in the request path.

Email & SMSResend + MSG91

Resend for transactional email with React templates. MSG91 for Indian SMS, where it is materially cheaper than Twilio; Twilio for international.

PaymentsRazorpay, then Stripe

Razorpay first for UPI, which the product already assumes. Stripe for international subscriptions. Split payouts if the platform ever takes a cut of customer bookings.

AnalyticsTinybird + PostHog

Tinybird (managed ClickHouse) ingests page-view and click events straight from the edge and serves the dashboard charts. PostHog for product analytics on the editor itself — where people drop out of onboarding.

AISmall embeddings + a routed LLM

An inexpensive embedding model over knowledge passages; a small fast model for synthesis, behind a gateway so it can be swapped. Keep the demo's honest fallback: below a confidence threshold, say so and offer a booking.

Custom domainsCloudflare for SaaS

Certificate issuance and renewal per customer domain through one API call, instead of running ACME ourselves.

QualityPlaywright + Vitest + Sentry

The demo's verification scripts are already Playwright-shaped. Sentry for errors, Checkly for synthetics against real published pages.

Trade-offs

The choices worth defending.

Considered and passed over

Reasonable alternatives

  • Remix or plain React on Cloudflare Workers. Cheaper and closer to the metal, but we would rebuild per-profile incremental rendering ourselves — the thing the whole design depends on.
  • A headless CMS. Tempting for blocks, but the editor is the product. Outsourcing the content model means fighting someone else's opinions in the one place we differentiate.
  • MongoDB. JSONB in Postgres gives the same flexibility for block props while keeping joins, transactions, row-level security and vectors in one engine.
  • A vector database on day one. pgvector is enough until roughly 50M vectors. Adding a second datastore before it is needed buys latency and ops work, not capability.
Non-negotiable

Where flexibility costs too much

  • The public page is server-rendered and cacheable. A client-side SPA would forfeit search indexing and the entire caching argument at once.
  • Block props stay schemaless. A column per block field turns every new block into a migration.
  • Media egress is priced before it is built. Picking storage on convenience is a decision that is unpickable at 50TB.
  • Page views never become rows. Aggregate at the edge from the first deploy, not when the primary starts smoking.

Risk

What breaks first, and what to decide now.

Fails in this order

Three predictable failures

  • Analytics writes. A row per view kills the primary long before traffic does. Aggregate at the edge from the first deploy.
  • Image bandwidth. Unoptimised media outgrows every other line on the bill. Resize on demand, modern formats, long cache lives.
  • Model cost per answer. Assistant usage scales with visitors, not customers. Cache aggressively, answer only on a confident match, cap knowledge base size per plan.

Decide before writing code

  • Tenancy model. Shared tables with row-level security are right to roughly a million profiles — but choose the shard key now, not later.
  • The publish pipeline. The contract between an edit and a purged CDN path is the core of the system; everything else is replaceable.
  • Where media lives. Migrating 50TB later is a project in its own right.
  • What a page view costs. Measure it in Phase 0 so Phase 3 holds no surprises.
